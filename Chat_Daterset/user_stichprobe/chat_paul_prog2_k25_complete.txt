## Aufgabe 1.1: Funktionale Interfaces in Java – Das Konzept

Bevor wir zum Code kommen, kurz die Idee: **Funktionale Interfaces** sind Java-Interfaces mit **genau einer abstrakten Methode**. Sie erlauben es, Lambda-Ausdrücke (also anonyme Funktionen) als Parameter zu übergeben.

Java stellt im `java.util.function`-Paket vorgefertigte funktionale Interfaces bereit. Die vier wichtigsten für diese Aufgabe sind:

| Interface | Signatur | Bedeutung |
|-----------|----------|-----------|
| `UnaryOperator<T>` | `T apply(T t)` | Eingabe → Ausgabe (gleicher Typ) |
| `IntBinaryOperator` | `int applyAsInt(int a, int b)` | Zwei `int` → ein `int` |
| `BiFunction<T, U, R>` | `R apply(T t, U u)` | Zwei Eingaben → beliebiger Rückgabetyp |
| `Predicate<T>` | `boolean test(T t)` | Eingabe → `true`/`false` |

## Lambda-Ausdrücke: Das Konzept

Ein **Lambda-Ausdruck** ist eine **anonyme Funktion** – also eine Funktion ohne Namen, die du direkt an der Stelle definierst, wo du sie brauchst. Statt eine separate Methode zu schreiben, kannst du das Verhalten "inline" angeben.

### Der Aufbau (Java-Syntax)

```java
(Parameter) -> { Rumpf }
```

| Teil | Bedeutung |
|------|-----------|
| `Parameter` | Eingabewerte (kann 0, 1 oder mehrere sein) |
| `->` | Pfeil, trennt Parameter vom Rumpf |
| `Rumpf` | Der Code, der ausgeführt wird |

---

## Konkrete Beispiele

### Beispiel 1: Ein Parameter, einfacher Ausdruck
```java
// Lambda: nimm einen int, gib int + 3 zurück
i -> i + 3

// Entspricht dieser anonymen Funktion:
int irgendeineFunktion(int i) {
    return i + 3;
}
```

### Beispiel 2: Zwei Parameter, mit Typangabe
```java
// Lambda: zwei ints, berechne (a % 3) + (b * 5)
(int a, int b) -> (a % 3) + (b * 5)
```

### Beispiel 3: Mehrzeiliger Rumpf
```java
(a, b) -> {
    String ergebnis = "First: " + a + ", Second: " + b;
    return ergebnis;
}
```

---

## Warum heißt das so? (Kurzer historischer Kontext)

Der Name kommt aus dem **Lambda-Kalkül**, einem mathematischen Formalismus von Alonzo Church (1930er). Dort schrieb man Funktionen als `λx.x+3` – das griechische Lambda `λ` stand für "anonyme Funktion". In Java wurde daraus der Pfeil `->`.

---

## Der entscheidende Punkt für deine Aufgabe

Lambda-Ausdrücke können **als Parameter übergeben werden**, aber nur wenn der Parameter-Typ ein **funktionales Interface** ist – also ein Interface mit genau einer abstrakten Methode.

Der Lambda "passt sich automatisch an" das Interface an. Wenn du also `i -> i + 3` übergibst, sagt Java: *"Ah, das ist eine Funktion mit einem `int`-Parameter und `int`-Rückgabe – das passt zu `UnaryOperator<Integer>`!"*

---

- Was gibt er zurück? **Einen `int`** (`i + 3`)
- Eingabe- und Ausgabetyp sind **gleich** (beide `int`)

   ## `reduce()` – Aggregation zu einem Wert
   
   Nach den Suchoperationen (`findAny`, `findFirst`) wird nun die **Reduktion** eingeführt: Kombination aller Stream-Elemente zu einem einzelnen Ergebnis.
   
   ### Beispiel: Maximum-Preis finden
   ```java
   Optional<Integer> maxPrice = catalog.stream()
       .map(Product::getPrice)      // Stream<Product> → Stream<Integer>
       .reduce(Integer::max);        // Kombiniere zu einem Maximalwert
   ```
   
   ### Typ-Transformation im Stream:
   | Schritt | Typ | Operation |
   |---------|-----|-----------|
   | `catalog.stream()` | `Stream<Product>` | Start |
   | `.map(...)` | `Stream<Integer>` | Extraktion |
   | `.reduce(...)` | `Optional<Integer>` | Aggregation |
   
   ### Warum `Optional<Integer>`?
   - Bei **leerem Stream** kein definiertes Maximum → `Optional.empty()`
   - Vermeidet `null`-Rückgabe und potenzielle `NullPointerException`
   
   Die visuelle Darstellung zeigt den iterativen Vergleich: `max(2499, 1899) → 2499`, dann `max(2499, 799) → 2499`, usw. bis zum finalen Maximum von `89900` (Laptop).

   ## Lazy Evaluation – Grundlagen
   
   Diese Folie führt das zentrale Konzept der **verzögerten Auswertung (Laziness)** ein, das die Effizienz von Streams ermöglicht.
   
   ### Beispiel-Stream-Pipeline:
   ```java
   String firstCheapProduct = catalog.stream()
       .filter(p -> p.isAvailable())           // Zwischenoperation (lazy)
       .filter(p -> p.getPrice() < 1000)       // Zwischenoperation (lazy)
       .map(p -> p.getName() + " - " + (p.getPrice() / 100.0) + " €")  // Zwischenoperation (lazy)
       .findFirst()                            // Terminale Operation (eager)
       .get();                                 // Extraktion aus Optional
   ```
   
   ### Schlüsselunterscheidung:
   | Operationstyp | Beispiele | Ausführung |
   |---------------|-----------|------------|
   | **Zwischenoperation** | `filter`, `map`, `sorted` | Lazy – nur Deklaration, keine Ausführung |
   | **Terminale Operation** | `findFirst`, `collect`, `reduce` | Eager – startet die gesamte Pipeline |
   
   **Warum Lazy?** Ohne Laziness würde jede Operation den **gesamten Datensatz** durchlaufen – bei 1 Millionen Produkten und 3 Filtern: 3 Millionen Operationen. Mit Laziness: nur so viele wie nötig (siehe nächste Folie).

## Warum `UnaryOperator<T>`?

| Eigenschaft | Passt zu deinem Lambda? |
|-------------|------------------------|
| **Ein Parameter** | ✅ `i -> ...` hat einen Parameter |
| **Gleicher Ein-/Ausgabetyp** | ✅ `int` → `int` (bzw. `Integer` → `Integer`) |
| **Rückgabe wird weiterverwendet** | ✅ Das Ergebnis soll zurückgegeben werden |

`UnaryOperator<T>` erweitert `Function<T, T>` – spezialisiert also auf den Fall, wo Eingabe und Ausgabe identisch sind.

> **Kleine Feinheit:** Da wir mit primitiven `int` arbeiten, wäre eigentlich `IntUnaryOperator` noch effizienter (kein Boxing/Unboxing). Aber `UnaryOperator<Integer>` funktioniert auch und ist oft in Übungen akzeptiert. Die Musterlösung zeigt `UnaryOperator<Integer>`.

## Generics: Das `<T>` in `UnaryOperator<T>`

Das `T` steht für **Typ-Parameter** (Type Parameter) – ein Platzhalter für einen beliebigen Datentyp. Das Konzept nennt sich **Generics** (generische Typen).

### Die Idee

Statt für jeden Datentyp eine eigene Klasse zu schreiben, definierst du **eine** Klasse/Methode, die mit **beliebigen** Typen funktioniert.

| Schreibweise | Bedeutung |
|------------|-----------|
| `UnaryOperator<Integer>` | Ein Operator, der `Integer` nimmt und `Integer` zurückgibt |
| `UnaryOperator<String>` | Ein Operator, der `String` nimmt und `String` zurückgibt |
| `UnaryOperator<Double>` | Ein Operator, der `Double` nimmt und `Double` zurückgibt |

---

## Konkretes Beispiel

```java
// Definition des Interfaces (vereinfacht):
public interface UnaryOperator<T> {
    T apply(T t);  // Nimmt T, gibt T zurück
}

// Verwendung mit verschiedenen Typen:
UnaryOperator<Integer> addThree = i -> i + 3;     // Integer → Integer
UnaryOperator<String> toUpper = s -> s.toUpperCase(); // String → String

Integer result1 = addThree.apply(10);   // ergibt 13
String result2 = toUpper.apply("hello"); // ergibt "HELLO"
```

---

## Warum nicht einfach `Object`?

Vergleiche:

| Mit `Object` (schlecht) | Mit `T` (gut) |
|------------------------|---------------|
| `Object apply(Object o)` | `T apply(T t)` |
| Keine Typprüfung zur Compile-Zeit | Compiler prüft Typen |
| Laufzeitfehler möglich | Sicherheit zur Compile-Zeit |
| Casting nötig: `(Integer) result` | Kein Casting nötig |

Mit Generics sagst du dem Compiler: *"Hier kommt ein bestimmter Typ rein, und derselbe Typ kommt raus."*

---

   - **Flexible**: Behavior Parametrization

   ## Stateful Operations – Zustandsbehaftung
   
   **Definition**: Operationen, die **Kontextinformationen** aus bisherigen Stream-Elementen benötigen.
   
   **Formale Beschreibung:**
   ```
   Output(element_i) = f(element_i, lambda, context(elements_0...i-1))
   ```
   
   **Konsequenzen:**
   - **Zwischenspeicherung** notwendig (z.B. alle Elemente für `sorted`)
   - **Höherer Speicherbedarf**: O(n) im schlimmsten Fall
   - **Eingeschränkte Parallelisierung**: Muss Synchronisation berücksichtigen
   
   **Konkrete Beispiele:**
   
   | Operation | Benötigter Zustand | Speicherbedarf |
   |-----------|-------------------|----------------|
   | `sorted()` | Alle Elemente zur Sortierung | O(n) |
   | `distinct()` | HashSet der gesehenen Elemente | O(n) |
   | `limit(n)` | Zähler der bereits durchgelassenen Elemente | O(1) |
   | `peek()` | Kann Zustand für Debugging halten | Variabel |
   
   **Wichtig**: Stateful Operations sind oft notwendig (Sortierung, Duplikatentfernung), aber teurer als stateless Alternativen.

## Warum nicht `IntIntOperator`?

Es gibt kein `IntIntOperator`, weil:

   **Grundlegende Unterschiede zwischen Scala- und Java-Collections:**
   
   | Aspekt | Scala | Java |
   |--------|-------|------|
   | Standardverhalten | **Immutable** (unveränderlich) | Mutable (veränderlich) |
   | Funktionale Operationen | Direkt auf Collections verfügbar | Erst via `.stream()` konvertieren |
   | API | Einheitlich über alle Typen | Unterschiedlich (List vs Set vs Map) |
   | Parallelisierung | Eingebaut einfach | Streams mit `.parallelStream()` |
   
   **Architektur:** `scala.collection` enthält nur Traits (Supertypen), die konkreten Implementierungen liegen in `immutable` und `mutable`. Das ermöglicht Polymorphismus: Ein Parameter vom Typ `scala.collection.Seq` akzeptiert sowohl `immutable.List` als auch `mutable.ArrayBuffer`.

   Inhalt:
   **`List` (immutable) vs. `ListBuffer` (mutable)**
   
   **`List` – immutable:**
   ```scala
   val products = List("T-Shirt", "Kochbuch", "Smartwatch")
   
   // Dies funktioniert NICHT:
   products += "Bluetooth-Lautsprecher"  // Fehler: += nicht definiert
   products(0) = "USB-Stick"             // Fehler: keine Index-Zuweisung
   products.remove(1)                    // Fehler: remove nicht verfügbar
   
   // Stattdessen: Neue Liste erzeugen
   val updated = "USB-Stick" :: products.tail  // Kopf ersetzen
   ```
   
   **Warum `ListBuffer`?**
   - `List` mit `::` vorne anfügen ist effizient, aber umgekehrte Reihenfolge
   - `ListBuffer` erlaubt effizientes `+=` (hinten anfügen) für Akkumulation
   - Nach Fertigstellung: `.toList` für immutable Ergebnis
   
   **Pattern:** Mutable für Aufbau, immutable für Speicherung – das Scala-Idiom für Performance bei Erhalt der Unveränderlichkeit.

   **Zusammenfassung: `ListBuffer`-Eigenschaften**
   
   - **Zweck:** Effizientes schrittweises Erzeugen und Ändern von Listen

## `Predicate<T>` – Deine Lösung

| Eigenschaft | Passt zu deiner Aufgabe? |
|-------------|------------------------|
| Ein Parameter | ✅ `i -> ...` hat einen Parameter |
| Rückgabe `boolean` | ✅ `i > 5` ist ein boolean-Vergleich |

Das Interface `Predicate<T>` hat die Signatur:
```java
boolean test(T t)
```

---

## Die vollständige Lösung

```java
public static List<Integer> filterIntegers(List<Integer> nums, Predicate<Integer> p) {
    List<Integer> output = new ArrayList<>();
    for (Integer i : nums) {
        if (p.test(i)) {  // ← Predicate mit .test() aufrufen!
            output.add(i);
        }
    }
    return output;
}
```

**Wichtig:** Bei `Predicate` heißt die Methode `test()`, nicht `apply()`!
